# 10. PostgreSQL + Qdrant Retrieval Contract

**Version:** 1.0  
**Last Updated:** 2026-07-17  
**Status:** Normative final contract  
**Audience:** backend, database, ingestion, retrieval partners

This file is the deployable source of truth for PostgreSQL and Qdrant. If an older database,
Qdrant, ingestion, or retrieval guide conflicts with this file, this file wins.

## 1. Ownership and invariants

```text
Canonical Markdown storage = authoritative ingestion input
PostgreSQL                = canonical business metadata, chunk content, parent relation
Qdrant                    = disposable Child-vector index and structural retrieval payload
```

Hard rules:

- Use exactly the 9 PostgreSQL tables defined below in schema `css`.
- Store Parent and Child chunks in PostgreSQL; embed and index Child chunks only.
- Never use a PostgreSQL integer ID as `chunk_key` or primary Qdrant identity.
- Generate Qdrant point ID deterministically from `version_key + chunk_key`.
- Do not store canonical chunk content in Qdrant payload. Hydrate final content from PostgreSQL.
- Rebuild Qdrant from canonical Markdown -> parser -> chunker -> embedding; PostgreSQL chunk rows
  alone do not contain all structural metadata needed to recreate payload in the MVP.
- Dense and sparse candidates must use the same eligibility policy before fusion.

## 2. PostgreSQL physical contract

### 2.1 Platform

```text
PostgreSQL: 17
Schema:     css
Encoding:   UTF-8
FTS config: simple
```

Vietnamese sparse retrieval uses PostgreSQL `simple` FTS. Query normalization belongs to the
retrieval service; the database contract does not install a custom Vietnamese dictionary.

### 2.2 Executable DDL

Partners may use this DDL to create a clean database directly. If Alembic already manages a
database with data, create a new migration that converges to this contract instead of editing an
applied migration.

Executable file: `infrastructure/postgres/bootstrap/001_create_retrieval_schema.sql`.

Choose exactly one provisioning path for a clean database:

- direct bootstrap SQL; or
- `alembic upgrade head` after the Alembic models/migration have been reconciled to this contract.

Do not run both against the same empty database. The Docker init file only creates schema `css`
so it does not compete with Alembic or the explicit bootstrap script.

```sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS css;

CREATE TABLE css.departments (

    code        VARCHAR(20)  NOT NULL UNIQUE,

);

    checksum                VARCHAR(64)  NOT NULL,
    extra_metadata          JSONB,
    ocr_status              VARCHAR(50)  NOT NULL DEFAULT 'not_started',
    review_status           VARCHAR(50)  NOT NULL DEFAULT 'not_reviewed',
    rag_status              VARCHAR(50)  NOT NULL DEFAULT 'not_indexed',
    status_note             TEXT,
    created_at              TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at              TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_document_versions_ocr_status CHECK (
        ocr_status IN ('not_started', 'processing', 'need_review', 'failed', 'done')
    ),
    CONSTRAINT chk_document_versions_review_status CHECK (
        review_status IN ('not_reviewed', 'reviewing', 'need_fix', 'approved', 'rejected')
    ),
    CONSTRAINT chk_document_versions_rag_status CHECK (
        rag_status IN ('not_indexed', 'chunked', 'embedded', 'indexed', 'published', 'deactivated', 'failed')
    ),
    CONSTRAINT chk_document_versions_published CHECK (
        rag_status <> 'published' OR (ocr_status = 'done' AND review_status = 'approved')
    )

CREATE TABLE css.document_chunks (

    document_version_id INTEGER      NOT NULL REFERENCES css.document_versions(id) ON DELETE CASCADE,
    parent_chunk_id     INTEGER      REFERENCES css.document_chunks(id) ON DELETE CASCADE,
    chunk_key           VARCHAR(255) NOT NULL,
    chunk_index         INTEGER      NOT NULL,
    chunk_type          VARCHAR(20)  NOT NULL,

    content             TEXT         NOT NULL,
    page_start          INTEGER,
    page_end            INTEGER,
    token_count         INTEGER,
    qdrant_point_id     VARCHAR(255) UNIQUE,
    index_status        VARCHAR(50)  NOT NULL DEFAULT 'not_indexed',
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_document_chunk_key UNIQUE (document_version_id, chunk_key),
    CONSTRAINT uq_document_chunk_index UNIQUE (document_version_id, chunk_index),
    CONSTRAINT chk_document_chunks_type CHECK (chunk_type IN ('parent', 'child')),
    CONSTRAINT chk_document_chunks_parent CHECK (
        (chunk_type = 'parent' AND parent_chunk_id IS NULL)
        OR (chunk_type = 'child' AND parent_chunk_id IS NOT NULL)
    ),
    CONSTRAINT chk_document_chunks_heading_path CHECK (jsonb_typeof(heading_path) = 'array'),
    CONSTRAINT chk_document_chunks_page_start CHECK (page_start IS NULL OR page_start >= 1),
    CONSTRAINT chk_document_chunks_page_end CHECK (page_end IS NULL OR page_end >= 1),
    CONSTRAINT chk_document_chunks_page_range CHECK (
        page_start IS NULL OR page_end IS NULL OR page_start <= page_end
    ),
    CONSTRAINT chk_document_chunks_token_count CHECK (token_count IS NULL OR token_count >= 0),

    status              VARCHAR(50)  NOT NULL DEFAULT 'pending',
    current_step        VARCHAR(100) NOT NULL DEFAULT '',
    total_chunks        INTEGER,
    processed_chunks    INTEGER      NOT NULL DEFAULT 0,
    error_message       TEXT,
    started_at          TIMESTAMPTZ,
    finished_at         TIMESTAMPTZ,
    created_by          VARCHAR(100),
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_ingestion_jobs_status CHECK (
        status IN ('pending', 'processing', 'completed', 'failed')
    ),
    CONSTRAINT chk_ingestion_jobs_total CHECK (total_chunks IS NULL OR total_chunks >= 0),
    CONSTRAINT chk_ingestion_jobs_processed CHECK (processed_chunks >= 0)

CREATE TABLE css.document_recipients (
    document_version_id INTEGER NOT NULL REFERENCES css.document_versions(id) ON DELETE CASCADE,

    display_order        INTEGER     NOT NULL DEFAULT 0,

CREATE INDEX ix_documents_document_type_id ON css.documents(document_type_id);
CREATE INDEX ix_documents_audience_gin ON css.documents USING GIN (audience);
CREATE INDEX ix_document_versions_document_id ON css.document_versions(document_id);
CREATE INDEX ix_document_versions_eligibility ON css.document_versions(review_status, rag_status);
CREATE INDEX ix_document_versions_is_latest ON css.document_versions(document_id, is_latest);

    ON css.document_versions(document_id) WHERE is_latest = TRUE;
CREATE INDEX ix_document_chunks_version_type_order
    ON css.document_chunks(document_version_id, chunk_type, chunk_index);
CREATE INDEX ix_document_chunks_parent ON css.document_chunks(parent_chunk_id);
```

| Field | Purpose |
|---|---|
| `documents.id` | Internal PostgreSQL PK |
| `documents.document_key` | Stable document identity |
| `document_versions.id` | Internal PostgreSQL PK |
| `document_versions.version_key` | Stable version identity |

## 3. Qdrant physical contract

### 3.1 Collection

Executable bootstrap: `infrastructure/qdrant/bootstrap_collection.py`.

Run it with the backend environment after setting `QDRANT_URL` and optional
`QDRANT_API_KEY`. The script is non-destructive: it creates the normative collection, verifies
an existing collection, and creates the required payload indexes. It does not recreate an
incompatible collection.

```text
Collection:             ctu_chunks_bge_m3
Vector name:            embedding
Embedding model:        BAAI/bge-m3
Vector dimension:       1024
Distance:               Cosine
Normalize embeddings:   true
Points:                 Child chunks only
```

Do not silently reuse a collection whose vector name, dimension, distance, or model differs.
Create a new collection when changing embedding model or dimension.

```http
PUT /collections/ctu_chunks_bge_m3
Content-Type: application/json

{
  "vectors": {
    "embedding": {"size": 1024, "distance": "Cosine"}
  }
}
```

### 3.2 Point ID

```python
from uuid import NAMESPACE_URL, uuid5


def make_point_id(version_key: str, chunk_key: str) -> str:
    return str(uuid5(NAMESPACE_URL, f"ctu-student-service/chunk/{version_key}/{chunk_key}"))
```

Same `version_key + chunk_key` must always produce the same point ID. Upsert is idempotent.

## 4. Cross-store ingestion lifecycle

```text
1. Validate canonical Markdown and metadata.
2. Short PostgreSQL transaction:
   - upsert Document/DocumentVersion/recipients;
   - insert Parent rows;
   - resolve parent_chunk_key -> parent_chunk_id;
   - insert Child rows with index_status=not_indexed;
   - update IngestionJob;
   - commit.
3. Outside PostgreSQL transaction:
   - create embedding text for Child rows;
   - embed Child rows;
   - upsert deterministic Qdrant points.
4. New short PostgreSQL transaction:
   - write qdrant_point_id on each Child;
   - set Child index_status=indexed;
   - set version rag_status=indexed;
   - set job completed;
   - commit.
5. Publish separately after validation: rag_status=published.
```

On embedding/Qdrant failure, keep canonical PostgreSQL data, set job/version failure state in a
new transaction, and retry idempotently. Never hold a PostgreSQL transaction across a network
call.

When replacing a published version, perform one PostgreSQL transaction:

```text
new version: is_latest=true, rag_status=published
old version: is_latest=false, rag_status=deactivated
```

After any publish, deactivate, latest-version, audience, or filterable metadata change, update the
matching Qdrant payloads with an idempotent `set_payload` operation. Record/retry synchronization
failure through the ingestion job. Temporary Qdrant drift must not leak into an answer because
PostgreSQL eligibility is revalidated during hydration.

## 5. Shared retrieval eligibility

Dense Qdrant search and PostgreSQL FTS must apply the same eligibility domain before fusion.

Mandatory for student chatbot retrieval:

```text
review_status = approved
rag_status = published
audience contains sinh_vien or cong_khai
chunk_type = child
index_status = indexed          # PostgreSQL sparse side
qdrant_point_id IS NOT NULL     # PostgreSQL sparse side
```

`is_latest` is a ranking preference, not a hard eligibility filter. Do not put
`is_latest=true` in the PostgreSQL `WHERE` clause or Qdrant `must` filter. Superseded versions
must be explicitly `deactivated`; retrieval may prefer `is_latest=true` after fusion or during
reranking.

Context filters such as `document_key`, `version_key`, `document_type`, and `domain` are added to
both dense and sparse paths. They do not replace eligibility.

### 5.1 Qdrant dense filter

```json
{
  "must": [
    {"key": "review_status", "match": {"value": "approved"}},
    {"key": "rag_status", "match": {"value": "published"}},
    {"key": "audience_student", "match": {"value": true}},
    {"key": "chunk_type", "match": {"value": "child"}}
  ]
}
```

### 5.2 PostgreSQL sparse query

```sql
WITH query AS (
    SELECT websearch_to_tsquery('simple', :query_text) AS value
)
SELECT
    c.id AS postgres_chunk_id,
    c.qdrant_point_id,
    c.chunk_key,
    c.parent_chunk_id,
    c.content,
    v.version_key,
    v.is_latest,
    d.document_key,
    ts_rank_cd(to_tsvector('simple', c.content), query.value) AS sparse_score
FROM css.document_chunks AS c
JOIN css.document_versions AS v ON v.id = c.document_version_id
JOIN css.documents AS d ON d.id = v.document_id
CROSS JOIN query
WHERE c.chunk_type = 'child'
  AND c.index_status = 'indexed'
  AND c.qdrant_point_id IS NOT NULL
  AND v.review_status = 'approved'
  AND v.rag_status = 'published'
  AND d.audience ?| ARRAY['sinh_vien', 'cong_khai']
  AND to_tsvector('simple', c.content) @@ query.value
ORDER BY sparse_score DESC, v.is_latest DESC, c.chunk_index ASC
LIMIT :candidate_limit;
```

After sparse retrieval, fetch Qdrant payload by `qdrant_point_id` before structural expansion.

## 6. Retrieval order

```text
resolved query
-> dense Qdrant + sparse PostgreSQL candidates under the same eligibility
-> attach Qdrant payload to sparse-only candidates
-> RRF or weighted fusion by chunk_key
-> hydrate direct hits from PostgreSQL and revalidate canonical eligibility
-> rerank direct hits; prefer is_latest when relevance is otherwise comparable
-> structural parent/child/sibling/split expansion using Qdrant payload
-> hydrate expanded neighbors from PostgreSQL
-> deduplicate
-> source order
-> context budget
-> grounded answer and citations
```

Greeting/clarification runs before retrieval. An empty candidate list after a resolved query means
no result, not clarification.

## 7. Acceptance checks

### PostgreSQL

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'css'
ORDER BY table_name;
```

Expected: exactly 9 tables from section 2.2.

```sql
SELECT indexname
FROM pg_indexes
WHERE schemaname = 'css'
ORDER BY indexname;
```

Must include `ix_document_chunks_fts_child`, `ix_document_versions_eligibility`, and
`uq_document_versions_one_latest`.

### Qdrant

- Collection exists as `ctu_chunks_bge_m3`.
- Named vector `embedding` is 1024-dimensional Cosine.
- Every point is a Child and has all non-null required payload fields.
- No payload contains canonical `content`.
- `postgres_chunk_id` hydrates exactly one `css.document_chunks` row.
- Re-upserting the same `version_key + chunk_key` does not increase point count.

### Retrieval

- Dense and sparse paths exclude non-approved/non-published versions.
- Hydration drops a dense hit when its Qdrant eligibility payload is stale relative to PostgreSQL.
- Student path excludes documents without `sinh_vien` or `cong_khai` audience.
- A published non-latest version is still eligible; `is_latest` only affects ranking.
- A deactivated superseded version is not eligible.
- Sparse-only candidates receive Qdrant structural payload before expansion.
- Final answer content and citations use PostgreSQL-hydrated text.

## 8. Explicit non-goals

- No `validity_status`, `effective_date`, or `expiry_date` columns on `document_versions`.
- No separate document-version status table.
- No Parent vectors in the MVP.
- No canonical content in Qdrant payload.
- No custom Vietnamese FTS extension in the MVP.
- No HNSW tuning, quantization, multivector, or advanced reranker requirement in this contract.

## 9. Current implementation handoff

The provisioning contract is final, but the current runtime is not yet fully conformant:

- `backend/app/vectorstore/repository.py` still targets prototype collection `ctu_chunks_test`,
  stores `content` in payload, and does not emit the full structural/eligibility payload.
- The existing Alembic baseline represents the older 9-table model but does not contain every
  retrieval constraint/index in the bootstrap SQL.
- Retrieval still needs the shared eligibility policy, PostgreSQL hydration/revalidation, sparse
  FTS path, fusion, reranking, and structural expansion described above.

Do not point the prototype vectorstore writer at `ctu_chunks_bge_m3`. Reconcile the runtime to
this contract first. For a database that already has Alembic history or data, add a forward
migration; do not run the clean-database bootstrap file over it.
